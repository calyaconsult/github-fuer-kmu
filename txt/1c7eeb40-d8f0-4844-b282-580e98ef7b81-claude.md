# GitHub – längst nicht nur für Programmierer

Wer selbst programmiert oder IT-Projekte leitet, kennt natürlich `GitHub` und das dahinterstehende Werkzeug `git`. Ausserhalb der IT-Welt wissen jedoch die meisten nicht, dass es diese Plattform und dieses Programm gibt. Das ist schade, denn auch Personen und Unternehmen, die selbst keine Software entwickeln, können in hohem Mass davon profitieren.

`git` ist ein Programm zur Versionsverwaltung, das Linux-Erfinder Linus Torvalds 2005 für die Entwicklung des Linux-Kernels geschrieben hat. `git` funktioniert vollständig auf dem eigenen Computer und benötigt keinen Server. `GitHub` ist eine Internet-Plattform, die 2008 von Chris Wanstrath, Tom Preston-Werner, P. J. Hyett und Scott Chacon gegründet wurde und seit 2018 zu Microsoft gehört. Auf GitHub kann man `git`-Repositories online speichern, gemeinsam mit anderen daran arbeiten und sie – wenn gewünscht – öffentlich und damit weltweit zugänglich machen.

**Was macht `git`?** Grundlage der Arbeit mit `git` sind sogenannte "Repositories". Ein Repository ist im Kern ein ganz normaler Ordner, in dem man Dokumente ablegt. Zusätzlich speichert `git` darin, in einem versteckten Unterordner, die gesamte Versionsgeschichte. Obwohl `git` als Werkzeug für Software-Entwickler konzipiert wurde, müssen die Dokumente keineswegs Programm-Quelltexte sein. Im Prinzip kann jede Datei in einem Repository abgelegt werden.

`git` hält den Zustand des Repositorys in einzelnen Versionen fest. Das geschieht allerdings nicht automatisch: Sobald man einen Arbeitsschritt abgeschlossen hat, legt man selbst eine neue Version an, einen sogenannten "Commit". Dabei vermerkt `git`, welche Dateien neu hinzugekommen sind, welche geändert und welche gelöscht wurden, wer die Änderung vorgenommen hat und wann. Zu jedem Commit gehört ausserdem eine kurze Beschreibung, die erklärt, was geändert wurde.

Besonders stark ist `git` beim Umgang mit Textdateien, also Dokumenten, die aus reinem Text in Zeilen bestehen. Dazu gehören alle Programm-Quelltexte sowie Formate wie HTML, XML, Markdown, JSON, YAML oder CSV. Bei diesen Dateien kann `git` zwischen zwei Versionen genau anzeigen, welche Zeilen hinzugefügt, geändert oder entfernt wurden. So lässt sich einerseits nachvollziehen, was bei einer Bearbeitung im Einzelnen geändert wurde. Andererseits kann man jederzeit zu jeder früheren Version zurückkehren oder einzelne Änderungen gezielt rückgängig machen.

Anders verhält es sich bei Dateiformaten wie PDF, Word oder Excel. Sie sind keine reinen Textdateien, sondern sogenannte Binärdateien. Auch sie werden von `git` versioniert, und frühere Versionen lassen sich jederzeit wiederherstellen. `git` kann aber nicht anzeigen, was sich inhaltlich geändert hat, sondern nur, dass sich die Datei geändert hat. Außerdem wird bei jeder Änderung die vollständige neue Version gespeichert, was das Repository bei grossen Dateien schnell anwachsen lässt.

**Wozu kann ich als Nicht-Programmierer `git` nutzen?** Überall dort, wo Dokumente über längere Zeit entstehen, sich verändern oder von mehreren Personen bearbeitet werden. Typische Beispiele sind Konzepte, Anleitungen, Handbücher, Protokolle, Verträge in Entwurfsfassung, Webseiten-Inhalte, Konfigurationsdateien, Rezeptsammlungen oder auch eine Doktorarbeit. Statt Dateien wie «Konzept_final», «Konzept_final2» und «Konzept_final_wirklich» anzulegen, gibt es nur noch eine Datei, deren Geschichte `git` lückenlos festhält. Man sieht jederzeit, wer wann was geändert hat, und kann bei Bedarf zu einem früheren Stand zurückkehren.

Auch für die Zusammenarbeit ist `git` hilfreich. Mehrere Personen können parallel an denselben Dokumenten arbeiten, und `git` führt ihre Änderungen zusammen. Wo zwei Personen dieselbe Stelle unterschiedlich bearbeitet haben, meldet `git` einen Konflikt und lässt die Beteiligten entscheiden. Mit sogenannten «Branches» kann man ausserdem Entwürfe oder Varianten getrennt vom Hauptstand ausarbeiten und erst dann übernehmen, wenn sie fertig und freigegeben sind. Auf GitHub kommen weitere Möglichkeiten dazu: Änderungen können als «Pull Requests» zur Prüfung vorgeschlagen und kommentiert werden, Aufgaben lassen sich als «Issues» verwalten, und mit «GitHub Pages» kann man aus Textdateien kostenlos eine Webseite veröffentlichen.

Am meisten Nutzen bringt `git`, wenn man Dokumente als Textdateien führt, zum Beispiel in Markdown. Das ist eine einfache Auszeichnungssprache, mit der sich Überschriften, Listen, Hervorhebungen und Links in reinem Text festlegen lassen. Der Text kann danach bei Bedarf in Word, PDF oder HTML umgewandelt werden. Wer so arbeitet, profitiert von den Stärken von `git` bei Textdateien, also vom genauen Vergleich zweier Versionen.

**Brauche ich dazu einen Server?** Nein. Wie oben erwähnt, funktioniert `git` vollständig auf dem eigenen Computer. Ein Repository auf der Festplatte mit seiner gesamten Versionsgeschichte genügt, um die Änderungen an den eigenen Dokumenten zu verfolgen und frühere Stände wiederherzustellen. Einen Server oder eine Plattform braucht man erst, wenn man mit anderen zusammenarbeiten, die Dokumente öffentlich machen oder eine zusätzliche Sicherung ausserhalb des eigenen Rechners haben möchte. Dafür bietet sich GitHub an, es gibt aber auch Alternativen wie GitLab oder Bitbucket, und `git` lässt sich auch auf einem eigenen Server betreiben. Für Einzelpersonen und kleine Teams ist GitHub in der Grundversion kostenlos, und auch private Repositories, die nur für ausgewählte Personen sichtbar sind, sind möglich.

**Brauche ich Linux? Geht das auch auf Windows oder Mac?** Linux ist nicht nötig. Obwohl `git` für die Linux-Entwicklung geschrieben wurde, läuft es auf allen gängigen Betriebssystemen, also auch auf Windows und macOS. Die Installation ist unkompliziert: Für Windows gibt es ein Installationsprogramm auf der Webseite von `git`, auf dem Mac ist `git` oft schon vorhanden oder wird bei Bedarf mit den Entwicklerwerkzeugen von Apple nachinstalliert.

Auch die Bedienung über die Kommandozeile ist keine Voraussetzung. Es gibt eine Reihe grafischer Programme, die `git` bequem per Mausklick bedienbar machen, etwa «GitHub Desktop», «GitKraken» oder «Sourcetree». Viele Texteditoren, zum Beispiel «Visual Studio Code», haben `git`-Funktionen bereits eingebaut. Wer sich nur mit den wenigen Grundbefehlen vertraut macht, nämlich Dateien hinzufügen, einen Commit anlegen und Änderungen auf GitHub hochladen oder von dort herunterladen, kommt im Alltag bereits sehr weit. Die Einstiegshürde ist damit deutlich niedriger, als es der Ruf von `git` als Entwicklerwerkzeug vermuten lässt.

**Wann und wie ist GitHub für ein Ein-Personen-Unternehmen oder eine kleine Firma eine Option?** Immer dann, wenn im Unternehmen Inhalte entstehen, die sich ändern und deren Geschichte man nachvollziehen möchte. Das gilt längst nicht nur für Software-Firmen. Eine Beraterin kann ihre Konzeptvorlagen, Checklisten und Methodenbeschreibungen in einem Repository führen, ein Handwerksbetrieb seine Arbeitsanleitungen und Preislisten, ein Verlag oder eine Redaktion Manuskripte im Markdown-Format. Auch Webseiten lassen sich so verwalten: Die Inhalte liegen als Textdateien im Repository, und mit «GitHub Pages» wird daraus ohne eigenen Server eine veröffentlichte Webseite. Ebenfalls geeignet sind Dokumentationen, Schulungsunterlagen, Konfigurationsdateien, Buchhaltungs- oder Auswertungsdaten im CSV-Format sowie Vorlagen für Offerten und Verträge.

Besonders interessant wird GitHub, sobald mehrere Personen beteiligt sind. Das können Mitarbeitende sein, aber auch externe Fachleute, etwa eine Texterin, ein Grafiker oder ein Webentwickler. Man lädt sie in ein privates Repository ein, legt fest, wer nur lesen und wer auch ändern darf, und kann jederzeit nachvollziehen, wer was beigetragen hat. Mit «Issues» lassen sich Aufgaben und offene Punkte verwalten, ohne dass man dafür ein weiteres Werkzeug braucht, und «Projects» bietet eine einfache Übersicht in Form eines Boards. Änderungen von Dritten können als «Pull Request» vorgeschlagen werden, sodass man sie prüft, kommentiert und erst dann übernimmt.

Ein weiterer Vorteil ist die Sicherung. Ein Repository auf GitHub ist eine zusätzliche Kopie ausserhalb des eigenen Rechners, die sich von jedem Gerät aus herunterladen lässt. Fällt der Laptop aus oder geht er verloren, sind die Dokumente samt Versionsgeschichte nicht verloren. Ein vollwertiges Backup-Konzept ersetzt das allerdings nicht, denn es deckt nur die Dateien im Repository ab und nicht den Rest des Systems.

**Wie fängt man an?** Der Einstieg ist einfach und kostet nichts. Man legt ein Konto an, schaltet gleich die Zwei-Faktor-Authentifizierung ein und erstellt ein erstes Repository. Als Faustregel gilt: Geschäftliche Inhalte gehören in ein privates Repository. Öffentlich sollte nur sein, was ausdrücklich für die Allgemeinheit bestimmt ist. Für Einzelpersonen und kleine Teams reicht die Grundversion von GitHub in der Regel aus. Bezahlte Pläne bieten zusätzliche Verwaltungs- und Sicherheitsfunktionen, die erst für grössere Teams wichtig werden. Da sich Angebote und Preise ändern können, lohnt sich ein Blick auf die aktuelle Preisübersicht von GitHub. Als Werkzeug empfiehlt sich für den Anfang ein grafisches Programm wie «GitHub Desktop» oder ein Editor mit eingebauter `git`-Unterstützung, damit man nicht mit der Kommandozeile beginnen muss. Am besten probiert man es zuerst mit einem überschaubaren Projekt aus, etwa den eigenen Vorlagen oder der Dokumentation eines Arbeitsablaufs, bevor man grössere Teile des Unternehmens darauf aufbaut.

**Worauf sollte man achten?** Drei Punkte verdienen Aufmerksamkeit. Erstens der Datenschutz: GitHub gehört zu Microsoft, und die Daten liegen auf Servern ausserhalb der Schweiz. Wer mit Personendaten von Kundinnen und Kunden oder mit vertraulichen Unterlagen arbeitet, muss prüfen, ob das mit dem Schweizer Datenschutzgesetz, gegebenenfalls der DSGVO und den eigenen Vertraulichkeitszusagen vereinbar ist. Im Zweifel gehören solche Daten nicht ins Repository. Zweitens die Zugangsdaten: Passwörter, Schlüssel und Zugangscodes haben in einem Repository nichts verloren, auch nicht in einem privaten, denn einmal committet, bleiben sie in der Versionsgeschichte erhalten. Drittens die Dateiformate: Wie oben beschrieben, kommt `git` mit Word-, Excel- und PDF-Dateien nur eingeschränkt zurecht. Wer überwiegend damit arbeitet, hat von der Versionsverwaltung weniger Nutzen als jemand, der auf Textformate setzt. Für reine Zusammenarbeit an Office-Dokumenten sind Werkzeuge wie Microsoft 365 oder Google Workspace oft die bessere Wahl, und auch ein Nebeneinander ist gut möglich.

Wer die Daten lieber in der Schweiz oder auf eigener Infrastruktur halten möchte, findet in `git` selbst die Freiheit dazu: Das Programm ist nicht an GitHub gebunden. Alternativen wie GitLab oder das selbst betreibbare Forgejo bieten ähnliche Funktionen und lassen sich bei Bedarf auf einem eigenen Server oder bei einem Schweizer Hosting-Anbieter betreiben. Ein Umzug ist unkompliziert, weil die gesamte Versionsgeschichte im Repository selbst steckt und sich mitnehmen lässt.

> **⚠️ Achtung: Sensible Daten gehören nicht auf GitHub**
>
> Was einmal in einem Repository gelandet ist, lässt sich kaum je wieder vollständig entfernen. Das gilt besonders für Zugangsdaten, Kreditkartennummern und Personendaten.
>
> **Warum ist das so gefährlich?**
>
> - **Die Versionsgeschichte vergisst nichts.** Wer ein Passwort oder eine Kundenliste nachträglich aus einer Datei löscht, hat sie nur aus dem aktuellen Stand entfernt. In früheren Commits sind sie weiterhin vorhanden und für jeden einsehbar, der Zugriff auf das Repository hat.
> - **Öffentliche Repositories werden automatisch durchsucht.** Automatisierte Programme durchforsten GitHub laufend nach Zugangsschlüsseln, Passwörtern und Zahlungsdaten. Oft vergehen nur Minuten, bis ein versehentlich veröffentlichter Schlüssel missbraucht wird, etwa für Cloud-Rechenleistung auf Ihre Kosten, für den Zugriff auf Ihre Datenbank oder für Betrug mit Ihrem Zahlungskonto.
> - **Auch private Repositories sind nicht sicher genug.** Ein privates Repository schützt nur so lange, wie alle Zugriffsberechtigten vertrauenswürdig und ihre Konten gut gesichert sind. Eine versehentliche Freigabe, ein gestohlenes Zugangskonto oder eine Kopie auf dem Laptop eines ehemaligen Mitarbeiters genügt, und die Daten sind offengelegt.
> - **Kopien lassen sich nicht zurückrufen.** Sobald ein Repository öffentlich war, können Dritte es kopieren («Fork» oder «Clone») oder archivieren. Löschen Sie Ihr Repository danach, bleiben diese Kopien bestehen.
> - **Es drohen rechtliche Folgen.** Personendaten von Kundinnen, Kunden oder Mitarbeitenden unterliegen dem Schweizer Datenschutzgesetz und je nach Fall der DSGVO. Eine Offenlegung kann Meldepflichten auslösen, zu Bussen führen und den Ruf des Unternehmens nachhaltig schädigen. Bei Kreditkartendaten kommen zudem vertragliche Pflichten gegenüber Zahlungsdienstleistern hinzu. Berufs- und Geschäftsgeheimnisse sind ebenfalls geschützt.
>
> **Was gehört nicht ins Repository?**
>
> - Passwörter, API-Schlüssel, Tokens, private Schlüssel und Zertifikate
> - Kreditkarten- und Bankdaten
> - Kundenlisten, Personallisten, Lohn- und Gesundheitsdaten sowie andere Personendaten
> - Konfigurationsdateien mit Zugangsdaten (zum Beispiel `.env`-Dateien)
> - Vertrauliche Verträge, Offerten und interne Unterlagen, die nicht für Dritte bestimmt sind
>
> **Wie schützen Sie sich?**
>
> - Legen Sie eine Datei `.gitignore` an, in der Sie Dateien mit Zugangsdaten und sensiblen Inhalten von der Versionierung ausschliessen, **bevor** Sie den ersten Commit machen.
> - Verwalten Sie Zugangsdaten in einem Passwort-Manager oder in speziellen Geheimnis-Speichern, nicht in Dateien im Repository.
> - Aktivieren Sie die Zwei-Faktor-Authentifizierung für alle Konten mit Zugriff auf Ihre Repositories.
> - Nutzen Sie die Schutzfunktionen von GitHub wie «Secret Scanning» und «Push Protection», die versehentlich eingecheckte Schlüssel erkennen oder sogar das Hochladen blockieren. Prüfen Sie in den Einstellungen, welche Funktionen für Ihr Konto verfügbar sind.
> - Prüfen Sie vor jedem Commit kurz, welche Dateien Sie hinzufügen.
>
> **Was tun, wenn es doch passiert ist?**
>
> 1. **Gehen Sie davon aus, dass die Daten kompromittiert sind.** Ändern Sie betroffene Passwörter sofort, widerrufen Sie Schlüssel und Tokens und erzeugen Sie neue. Dieser Schritt ist wichtiger als das Aufräumen des Repositorys.
> 2. Bei Kreditkarten- oder Bankdaten informieren Sie umgehend den Zahlungsdienstleister oder die Bank und lassen Sie die betroffenen Karten oder Konten sperren.
> 3. Entfernen Sie die Daten anschliessend auch aus der Versionsgeschichte, zum Beispiel mit Werkzeugen wie `git filter-repo`. Das einfache Löschen der Datei im nächsten Commit genügt nicht.
> 4. Bei Personendaten prüfen Sie, ob eine Meldepflicht besteht, und ziehen Sie im Zweifel eine Fachperson für Datenschutz oder Recht bei.
>
> **Merksatz:** Im Zweifel gehören sensible Daten nicht ins Repository.
